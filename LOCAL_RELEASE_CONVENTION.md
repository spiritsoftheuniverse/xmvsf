# XMVSF local TEST release convention

**Effective with TEST 87.251.** This is a release discipline, not a new build system.

1. **GitHub is source control only.** No GitHub Actions, hosted builds, CI gates, monitoring, installers, or other remotely triggered build machinery. Native build and execution stay on the user's Windows/MSYS2 installation through the existing root `BUILD_TEST.bat` and `RUN_TEST.bat`.
2. **The normal BUILD_TEST path builds the game.** The accumulated ROM-free C++ test executables and Python source-assertion scripts are **not** run in the default batch path. They remain in the repository, unchanged and available only by explicitly setting `XMVSF_RUN_REGRESSIONS=1` in the local environment. Do not turn them on by default, or add new gates, scans, clean rebuilds, compiler fingerprints, or unrelated work to the user's build.
3. **Fix the code before release, not by testing on the user.** For each change, inspect the *current branch files*, make a small and coherent edit, check all touched symbols, declarations, includes, quotations, source-string references, shell nesting, and filename/version references before writing. An expected-source-text assertion is not proof of native correctness. Never invent, loosen, or suppress a failing test and present it as a fix.
4. **Publish one coherent checkpoint.** Apply related source and launcher changes in one commit against the exact observed branch head, so the branch never temporarily contains half of a version bump. Keep the three release surfaces aligned: root `BUILD_TEST.bat`, root `RUN_TEST.bat`, and `dev/dhc/BUILD_TEST.sh`. Advance the TEST number per user-requested release. Leave Stable and previous numbered TEST executables untouched.
5. **No unconditional additional compilation.** Keep the warm object cache and incremental native make dependency graph. Do not force `make clean`, `-B`, `-W`, unnecessary hash scans, or new always-run regression programs. A failed build preserves its logs and prior executables, and the launchers must never silently run an old TEST.
6. **Be precise about verification.** Source review and connector writes are **not** Windows native compilation. Never call a build "verified" or "running" unless its actual local native compile/run evidence exists. If a local log reports a failure, repair the exact failing code or misleading test, instead of piling on more release blockers. Preserve the full existing transcript at `test/build_logs/BUILD_TEST.log`.

This policy does **not** claim that optional regressions pass. It separates those developer diagnostics from the user's normal game build, without deleting their sources or affecting gameplay.
